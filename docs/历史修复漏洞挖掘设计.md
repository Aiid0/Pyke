# 历史修复漏洞挖掘模块设计

> 状态：项目级增量索引、按需深查及任务级只读线索接入已实现（2026-11-17）。适用于授权源码仓库与测试环境。

## 目标与入口

从 Git 历史中的显式安全修复、未标注的内部修复、后续补丁与回滚中提取研究线索，关注修复遗漏的平行入口及改动引入的回归。大量提交分批索引；已处理提交、筛选理由和每轮深查结论持久化，后续只对新提交或明确的问题继续分析。

前端左侧“功能 → 历史修复分析”是独立入口。用户选择已有 Git 项目，或在此导入仓库；点击“开启历史索引”后在后台同步。页面可查看索引量、候选量、断点、错误、分支历史改写，按完整 SHA 或日期检索，按文件读取有界差异，并对提交提出一轮具体的深查问题。每轮问题与结论都保留，页面自动刷新进行中的分析。

历史索引和深查以项目为单位运行，不创建渗透测试任务或自动生成漏洞报告。Git 源码任务仍使用导入时固定的源码快照；任务概览展示该版本可达的少量历史线索，Planner 每轮规划会收到最多三条简短摘要，并可使用只读工具检索候选、差异和已保存结论。Worker 和主 Agent 也可按需读取。Agent 先核对当前源码与反证，只有实际验证成立才沿现有事实、证据和报告流程登记发现。历史作业失败或尚未索引时，普通漏挖继续运行。

## 分层处理

| 层级 | 当前动作 | 持久化结果 |
| --- | --- | --- |
| 历史索引 | 对导入分支分批读取 SHA、父提交、时间、说明、路径及有界差异 | `project_history`、`project_history_refs`、`project_history_queue`、`project_history_commits` |
| 规则筛选 | 根据说明、路径和差异里的安全边界变化评分 | 提交评分、理由、规则版本及 `project_fix_candidates` 卡片 |
| 按需深查 | 用户指定提交和问题；独立后台作业读取有界 diff 并调用已配置的全局 LLM | `project_fix_analysis` 追加轮次；更新候选当前摘要和深度 |
| 实际验证 | 在授权测试范围内单独执行 | 普通任务的事实、证据与发现记录 |

规则筛选既检查 `security`、`fix`、`CVE` 等文本，也检查新增鉴权、输入校验、转义、签名/边界检查等行为。文本命中、规则评分和模型结论都不能当成已确认漏洞。大提交和差异截断会明确标记，方便之后按提交或文件细查。

模型深查提示要求说明修复意图、安全约束、可能遗漏的路径、回归假设、反证与未知条件。提交说明与差异一律作为不可信材料；模型调用没有工具权限，也不会执行提交里的指令。每次最多读取 20 KiB 差异，90 秒超时，输出预算 1200 tokens。分析失败保存可见状态；用户可以使用新的请求再次分析。完成的研究结果可作为任务级只读线索复用。

## 增量状态与恢复

历史对象库存放于项目私有的 `history.git`，与普通任务源码快照分开。一次同步先固定远端分支头，再把待处理 SHA 放入数据库队列；每批提交与队列断点在事务内提交。重试按项目及 SHA 去重，不从第一条重新筛选。继续同步时快进只处理新增历史；强制推送后标记不再可达的旧提交为孤立，保留其分析。浅克隆需要用户再次点击继续同步才能向更早历史推进；界面仅把导入分支显示为已覆盖范围。

深查请求先保存 `pending` 记录，按项目和请求幂等键去重。后台工作器从 PostgreSQL 原子领取作业，并保存 `job_id` 和租约；进程退出时，租约到期的 `running` 作业可再次领取。结论写入分析轮次，同时在同一事务更新候选摘要。多次深查追加新轮次，不覆盖旧判断。无全局 LLM 时不能启动深查，但历史索引和普通审计仍可使用。

数据库是进度、结论与队列的权威。项目 Git 凭据只用于导入或本次同步，不写入 Git 配置、日志、任务源码或分析记录。索引和深查各自独立限流；差异查询只接受已索引的提交 SHA 和该提交包含的文件路径。

## 服务接口与使用步骤

所有接口沿用项目 API 鉴权：

| 接口 | 用途 |
| --- | --- |
| `GET /api/projects/{id}/history` | 索引状态与进度 |
| `POST /api/projects/{id}/history/sync` | 开启或继续分支历史同步，私有仓可在本次请求提供凭据 |
| `GET /api/projects/{id}/history/commits` | 分页检索候选或按 SHA、日期检索提交 |
| `GET /api/projects/{id}/history/commits/{sha}/diff` | 读取提交或指定文件的有界差异 |
| `GET /api/projects/{id}/history/commits/{sha}/analyses` | 读取该提交的项目级分析轮次 |
| `POST /api/projects/{id}/history/commits/{sha}/analyses` | 提交 `{question,idempotency_key}`，返回作业 ID |
| `GET /api/tasks/{id}/history-leads` | 返回任务固定源码版本可达的前五条候选摘要 |

使用时先导入 Git 项目，再开启历史索引。候选出现后点开提交，核对筛选理由与差异，输入一个具体问题，例如“同一鉴权函数的其他调用者是否也有归属检查”。分析完成后在同一提交下继续提问，旧轮次始终可回看。需要更早的历史时继续同步；已有提交不会再次从头分析。绑定该项目的漏挖任务会在概览中显示可达线索，Planner 在后续规划轮次主动参考这些摘要；历史线索不会替代对当前源码的核实。

## 后续能力

后续可加入 PR/issue/review/release 元数据、CVE/GHSA 与仓库提交的核对、修复系列聚合、多分支与标签的独立水位、低成本模型辅助筛选，以及针对代码变化的定向复核。每项能力都应沿用项目级持久化状态、独立作业队列和有界输入。确认漏洞仍由授权测试中的实际证据决定。

## 验收

使用受控 Git 仓库覆盖普通提交、隐性安全修复、后续补丁和强制推送：索引批次可续跑，新提交只增量处理，旧结论保留；多次同幂等键请求只生成一轮分析；中断的深查可通过租约恢复；任务只读取绑定版本可达的候选，其他项目和不可达提交不会进入规划摘要；模型结论不会自行成为确认漏洞。构建与测试按仓库 `AGENTS.md` 执行。
