# 历史修复漏洞挖掘模块设计

> 状态：基础链路已实施（2026-11-17）；自动模型筛选与外部 PR/issue 元数据仍按后续批次推进。适用于用户授权的源码仓库与测试环境。
> 本文同时保留完整目标设计；下方「实施记录」说明当前可用范围。

## 1. 目标与现状

从公开 CVE/GHSA 对应的修复、普通提交与 PR 中的隐性安全修复、后续补丁和 revert 中提取研究线索，检查修复是否遗漏平行入口或在新代码中引入问题。结果应随着项目积累：中断后续跑，新任务复用已完成的项目级分析，用户或 Agent 能对单条线索继续深查，并保留旧判断及其依据。

导入路径仍用 `--depth=1 --single-branch --no-tags` 获取任务源码；历史对象库存放在项目的独立目录，任务快照不含 `.git`。`db.projects` 保存项目与目标提交，任务另存项目元数据快照。`vulnintel` 有持久化同步游标；探索图有意图、事实与发现，`report_finding` 有证据门槛。新模块沿用这些职责，不把 commit 猜测直接写为确认漏洞。

## 2. 用户流程与总体边界

1. Git 项目导入完成后，用户可开启“历史修复分析”；开启动作创建后台索引作业，页面立即返回。历史不可用不妨碍现有源码审计。ZIP 和目录导入只支持普通源码审计。
2. 项目来源选择器及任务详情显示历史范围、同步进度和候选卡片。用户可指定提交或时间范围、查看筛选理由、要求对某张卡片深入分析。默认优先处理目标提交之前的近期历史；向更早历史回溯是可续跑的后台工作。
3. 创建源码审计任务时，绑定的仍是导入时的固定源码提交。Planner 可查看该提交可达的历史候选，选取少量线索派发验证意图；Worker 读取受限的提交差异与当前源码，提交事实、反证和验证结果。
4. 新提交同步到项目历史后，旧任务和该已导入项目的源码版本不变。用户重新导入新版本并据此创建任务时，才使用新源码快照。项目级卡片可被同一项目的后续任务复用；跨项目复用需要先建立明确的仓库身份映射，不能仅凭 URL 或名称合并。“适用于目标提交”和“本任务已验证”必须逐任务判定。

项目级历史存储与任务源码目录隔离。Agent 不拿 Git 凭据，也不直接操作仓库对象库；历史只通过带项目/任务边界的只读接口访问。PR、issue、提交消息和源码注释均视作待分析资料，不能改变 Agent 权限、工具调用或审计范围。

## 3. 分层分析与持久化状态

| 层级 | 输入与动作 | 保存的结果 | “完成”的含义 |
| --- | --- | --- | --- |
| 索引 | 分批读取提交 SHA、父提交、分支可达性、时间、改动路径、变更规模、关联编号 | 提交元数据、仓库/分支水位和批次断点 | 该批提交可以检索；没有判定安全性 |
| 筛选 | 规则检查改动行为、测试、公开公告及后续修复；必要时用低成本模型解释 | 入选/排除理由、规则版本、置信度、待查问题 | 形成待研究候选；不是漏洞结论 |
| 深查 | 按候选读取有界 diff、修复前后代码、调用关系、平行入口 | 修复试图维护的安全约束、代码锚点、遗漏/回归假设、反证、未决问题 | 已完成这一轮源码分析；动态影响仍待验证 |
| 验证 | 对任务绑定版本在本地隔离环境或授权测试环境做最小对照 | 意图、执行记录、事实、附件、必要时确认漏洞 | 只对该任务、版本、条件和证据有效 |

筛选既看 `security`、`fix`、`CVE` 等文本，也看具体行为：新增授权或归属检查、输入规范化、边界/签名校验、转义、事务约束、错误处理、回归测试；follow-up 修复与 revert 提高优先级。文本命中不能单独把普通提交判为安全修复。排除也保留理由，避免下次全量重判。

深查沿两个问题展开：**旧问题还有没有未被覆盖的可达路径**，以及**新改动有没有破坏其他安全约束**。优先比较详情/列表/批量/导出/旧接口、共享函数的其他调用者、异常/重试/缓存/异步路径、不同分支的回补。必要时建立修复前、修复后、任务目标版本的对照；执行前确认代码版本及测试环境。无法验证时保留候选与缺失条件。

一张卡片可有多轮深查。后续请求应注明具体问题，例如“检查同一校验器的所有调用者”；新分析追加记录并更新当前摘要，不能覆盖旧证据与反证。卡片的状态与深度分开：`待筛选/待深查/分析中/已分析/需复核/失败可重试` 是工作状态，`已索引/已筛选/已深查/已验证` 是已达到的层级。页面分别统计，不能用“已分析提交数”混称为审计覆盖率。

## 4. 存储模型与续跑规则

PostgreSQL 是结构化状态的唯一权威；受控 Git 对象库只保存按需读取历史所需的原始对象。建议新增以下逻辑实体（具体 DDL 在实施时按现有 `db/schema.sql` 幂等迁移约定落地）：

| 实体 | 关键字段与约束 | 用途 |
| --- | --- | --- |
| `project_history` | `project_id` 唯一、启用状态、对象库存储标识、索引范围、上次错误 | 项目级历史入口；旧项目默认关闭 |
| `project_history_refs` | `(project_id, ref_name)` 唯一、已同步头 SHA、本轮固定头 SHA、遍历断点、运行状态 | 分支/标签各自续跑；记录历史改写 |
| `project_history_commits` | `(project_id, commit_sha)` 唯一、父提交、时间、摘要、改动路径、筛选状态和规则版本 | 去重的提交目录；按仓库与提交检索 |
| `project_fix_candidates` | `candidate_id`、`project_id`、修复系列、主提交、关联提交、评分、筛选理由、当前深度/状态、版本号 | 隐性修复与已知修复的统一卡片 |
| `project_fix_analysis` | `candidate_id`、轮次、目标提交、分析器版本、问题、源码锚点、安全约束、反证、未决项、结果 | 追加式分析历史；重复请求有幂等键 |
| `task_fix_leads` | `(task_id, candidate_id, target_revision)` 唯一、适用性、意图/事实/发现关联、验证状态 | 项目卡片进入某个任务后的独立结论 |

同一项目的提交按 SHA 去重，筛选状态按提交及筛选版本标记；深查按“候选 + 问题 + 目标提交 + 分析器版本”幂等。不同仓库里的同一 SHA 不跨项目合并。cherry-pick 可以归到同一修复系列，但各提交的可达性和适用版本分别保存。

同步时先固定本轮的远端分支头，再按有界批次遍历。**该批提交、分析状态与下一断点在同一数据库事务内提交**；中断时最多重做未提交的批次。不能以“第 N 条”作唯一游标，因为新提交和合并会改变位置。Git fetch 完成但数据库尚未提交时可安全重试；对象缺失、网络错误或空间不足保留断点、错误和重试时间，不把作业标完成。

每轮同步比较已保存头与新头。快进时只索引新增可达提交；强制推送或分支删除时重新计算可达性，把不再可达的提交标记为历史孤立记录，保留旧分析。旧项目若没有历史对象库，显示“未开启/历史不可用”，不凭项目 `revision` 假装已经索引。

分析版本升级只使受影响的筛选或深查结果进入 `需复核` 队列，保留原记录；目标版本变更仅重新计算候选适用性和涉及改动路径的任务级结论。一次作业由数据库租约/领取状态控制并发，进程退出后租约到期可重领。限制批次大小、单 diff 字节、对象库体积、并发数和模型预算；超过限制的提交记录为“待人工/按需展开”，不能静默略过。

## 5. 服务、Agent 与界面接入

服务端在项目 API 下增加历史状态、分页提交/候选列表、单卡详情、启动/继续同步、请求深查等接口；写操作需沿用项目鉴权与任务范围检查。长作业立即返回作业 ID，状态接口显示阶段、处理量、最近错误和可继续位置。读取 diff 按提交 SHA 和允许的路径查询，限制输出大小并支持按文件/片段展开；服务端验证提交属于该项目历史且对请求的目标版本适用。

Agent 工具建议为 `search_fix_candidates`（分页与过滤）、`get_fix_candidate`、`get_commit_diff`、`request_fix_analysis`。前三个只读；最后一个只是创建有预算的后台分析请求，不允许 Agent 自由执行 Git 命令或访问凭据。工具由 `PlannerTools`、`WorkerTools`、`MainAgentTools` 按角色登记，进入 `BuiltinToolSeeds`，遵循现有工具配置的禁用与自定义绑定。Planner 负责选择候选及派意图；Worker 负责单个边界的源码追踪和验证。项目级卡片可跨任务读取，任务级结果仅写回本任务探索图。

前端在项目选择器展示历史功能入口、状态和索引范围；任务详情增加“历史修复”视图，列出候选、筛选理由、目标版本适用性、分析深度、未决问题、验证状态和“继续深查”。默认分页，详细 diff 按需加载。界面明确区分“源码线索”“待验证”“已排除”“已确认”，并展示版本与证据来源。

`vulnintel` 的 CVE/GHSA 引用可帮助定位修复提交，但是否对应本项目及本版本仍需核对。确认漏洞沿用 `report_finding` 证据门槛；提交记录、PR 文本或模型分析都不能直接上报。验证过程写入 `record_fact` 和任务执行记录，必要时保存测试输出/截图；确认后报告引用提交、代码位置、目标版本及实际触发证据。项目卡片删除或重筛不得抹去已归档任务中的验证来源。

## 6. 实施批次与验收

**第一批：可续跑的基础能力。** Git 项目可选择开启历史索引；支持持久化提交目录、分支断点、手动指定提交或区间、候选卡片、单卡按需深查及项目/任务关联。页面能显示真实进度。旧项目保持原行为，用户可随后开启；ZIP 和目录项目显示功能不可用。

**第二批：自动筛选与编排。** 加入行为规则、已知漏洞关联、follow-up/revert 识别、候选排序与预算控制；Planner 只领取少量尚未验证的候选，Worker 的反证与结果回写卡片及任务图。

**第三批：持续增量与外部上下文。** 增量同步、分支历史改写处理、PR/issue/review/release 元数据、受影响卡片的定向复核。外部元数据拉取沿用维护出网配置；私有仓凭据只在用户授权的仓库范围内使用。

验收使用一个受控 Git 仓库，包含大量普通提交、没有 CVE 的安全修复、漏掉的平行入口、后续补丁、revert、合并与强制推送。至少验证：

1. 批次中断与进程重启后续跑；提交、候选和分析轮次不重复，已排除提交不再无故消耗模型预算。
2. 新增提交只增量处理；历史改写保留旧结论并正确标注适用性；旧任务的源码提交不变。
3. 两个绑定同一项目的任务复用项目卡片，但各自独立记录适用性、意图、反证和确认结果。
4. 单卡深入检索能保留前一轮分析；规则升级或相关源码变化只使受影响卡片进入复核。
5. 普通提交、缺少动态证据的安全修复猜测不会成为确认漏洞；实际验证成立后能沿现有事实、附件和报告链路追溯。
6. Git 凭据不出现在任务源码、Agent 工具响应、日志或导出物；历史作业失败不会阻断普通源码审计。

实施验证按仓库门禁执行 `go build ./...`、独立 PostgreSQL 上的相关 Go 测试，以及在 `web/` 中执行 `npx tsc --noEmit` 和 `NEXT_EXPORT=1 npx next build`。文档中每个完成状态必须对应可观察的数据库记录或验证证据。

## 7. 实施记录（2026-11-17）

已接入 Git 项目的历史开启与继续同步、项目级对象库、PostgreSQL 提交队列和批次续跑、可恢复的作业租约、按提交 SHA 去重的目录、分支头与历史改写记录。同步保留旧提交和分析，对当前分支不再可达的提交标记孤立；任务仍只使用导入时固定版本。页面展示索引数、候选数、待处理数、错误、回溯边界，支持按完整 SHA 和日期检索、按文件查看有界差异。

筛选目前使用提交说明、改动路径和新增代码中的安全边界规则，记录规则版本、评分与理由；大提交和超限差异形成待展开线索。候选卡片及多轮分析在库中留存。任务请求深查会写入探索图提示并唤醒规划者；Planner、Worker、主 Agent 可查当前版本可达的线索、读取差异摘录、追加分析和保存任务级排除/上报状态。任务级「已上报」必须引用本任务已有的漏洞记录；提交猜测本身不能直接成为确认漏洞。

尚待后续批次的目标：低成本模型筛选及预算队列、CVE/GHSA 与本仓库提交的核对关联、PR/issue/review/release 元数据拉取、多分支与标签的独立同步、修复系列聚合，以及根据目标代码变化的定向复核。当前 `project_history_refs` 记录导入分支；不把它显示为全部分支覆盖。历史对象库继续回溯需要用户再次点击同步，已处理提交不会重新从头分析。
